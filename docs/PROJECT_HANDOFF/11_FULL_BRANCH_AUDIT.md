# Полный аудит ветки cmp-protocol-v1

Дата аудита: 2026-08-07

Репозиторий: `FantomeKGZ/CoilMaster`

Ветка: `cmp-protocol-v1`

## Назначение документа

Этот файл является сводной картой фактической реализации ветки. Он нужен, чтобы новый чат или разработчик не начинал работу с устаревшего состояния `main`, не повторял уже выполненные этапы и не называл планы готовыми функциями.

Приоритет источников:

1. актуальный код ветки `cmp-protocol-v1`;
2. фактическая сборка и тесты;
3. тематические документы `docs/`;
4. каталог `docs/PROJECT_HANDOFF/`;
5. история чатов.

## 1. Масштаб ветки

Ветка `cmp-protocol-v1` значительно опережает `main` и содержит сотни коммитов разработки. Несмотря на название ветки, здесь реализуется не только протокол CMP, но и основная система CoilMaster:

- Arduino-контроллер станка;
- ESP32-сервисный контроллер;
- UART-доставка заданий и события намотки;
- журнал запусков;
- клиенты, двигатели и ремонты;
- склад провода;
- дополнительные материалы;
- калькуляция ремонта;
- расчёт проводников;
- мобильный и настольный веб-интерфейс;
- статический WEB-сервер с microSD;
- документация и CI.

Для продолжения разработки использовать именно эту ветку.

## 2. Архитектура контроллеров

### Arduino Uno

Роль: контроллер реального времени и физической безопасности.

Фактически присутствуют модули:

- конечный автомат намотки;
- ввод с клавиатуры и кнопок;
- физическая кнопка START;
- датчик Холла и источник витков;
- SSR-контроллер;
- LCD1602;
- buzzer;
- EEPROM-восстановление;
- UART-транспорт событий;
- очередь подтверждений и повторов;
- конфигурация пинов и возможностей.

Ключевое правило безопасности:

- ESP32 и веб не включают SSR напрямую;
- физический запуск остаётся на Arduino;
- получение задания не означает разрешение запуска;
- при отказах безопасное состояние SSR должно быть OFF.

### ESP32

Роль: сервисы, данные, сеть и подготовка заданий.

Фактически присутствуют:

- Wi-Fi Access Point;
- WebServer;
- microSD;
- статический WEB-сервер;
- UART-приёмник и отправитель заданий;
- журнал намотки;
- склад провода;
- каталог материалов;
- клиенты, двигатели и ремонты;
- калькуляция;
- проводниковый калькулятор;
- API и WEB-обработчики.

## 3. Протокол и связь Arduino ↔ ESP32

### Фактический транспорт

В активном прикладном цикле используется строковый протокол кадров вида `CMP1|...`, а не только ранняя бинарная спецификация из старых документов.

Это важно: старые документы бинарного CMP нельзя считать единственным описанием работающего обмена.

### Реализовано

- отправка задания ESP32 → Arduino;
- принятие или отклонение задания;
- повторная отправка с ограничением;
- таймаут доставки;
- запрет перезаписи непрочитанного результата доставки;
- отмена ещё не отправленного задания;
- строгий разбор числовых полей UART;
- ACK/NACK для событий;
- события `RUN_STARTED` и `RUN_COMPLETED`;
- составная идентичность события:

```text
session_id + run_id + event_type
```

- проверка запуска до завершения;
- одна активная намотка внутри сессии;
- монотонный `run_id` в пределах сессии;
- защита от дублей.

### Не завершено

- устойчивое выделение `session_id`;
- неизменяемый снимок задания до доставки;
- полная связь `repair_id + motor_id + job_id + session_id + run_id + coil_index`;
- восстановление задания после перезапуска ESP32;
- обработка старого ACK после восстановления;
- полный снимок программы в журнале событий.

## 4. Общий CMP Core

В `Shared/Protocol/` присутствует полный набор модулей:

- Defines;
- Result;
- Flags;
- Command;
- Header;
- Packet;
- CRC;
- Buffer;
- Parser;
- Protocol;
- Dispatcher.

Также присутствуют host-side тесты и workflow `CMP Protocol Tests`.

Однако прикладной UART-поток Arduino/ESP32 имеет собственный строковый контракт. Перед дальнейшим развитием нельзя автоматически считать бинарный CMP и прикладные строки одной и той же полностью интегрированной реализацией. Нужна явная карта границ и план унификации либо документированного сосуществования.

### Реализованные функциональные области

- UART event receiver;
- winding journal;

- conductor calculator;
- conductor settings and persistence;
- web handlers for these modules.

### Известная точка создания задания

В `firmware/esp32/src/main.cpp` веб-запрос создаёт `OutgoingWindingJob`, присваивает текущие `jobId` и `sessionId`, разбирает программу витков и передаёт задание через `receiver.queueJob(job)`.

Текущие идентификаторы в этом пути формируются в RAM. Это не удовлетворяет утверждённому требованию устойчивого allocator/snapshot и является следующей активной областью.

## 7. Хранение данных на microSD

Основной формат — NDJSON и вспомогательные pending/tmp-файлы.

Используются или запланированы каталоги:

```text
/data/workshop/
/data/winding-runs/
/data/materials/
/web/
```

Реализованные правила целостности:

- подтверждённая операция сохраняет исторический снимок материала и цены;
- старая операция не пересчитывается по новой цене;
- UNKNOWN не превращается в CU автоматически;
- операции проверяют существование ремонта;
- поддерживается KGS_ONLY для соответствующих материальных операций;
- незавершённые материальные транзакции имеют recovery-механику;
- серверные итоги и контрольные признаки имеют приоритет над браузерным пересчётом.

Риски:

- линейный проход по крупным NDJSON-файлам;
- отсутствие индексов и пагинации для больших объёмов;
- необходимость ротации журналов;
- поведение при заполнении и повреждении SD требует комплексных испытаний.

## 8. Реестр мастерской

### Реализовано

- клиенты;
- двигатели;
- ремонты;
- API создания и чтения;
- mobile/desktop UI;
- выбор двигателя для ремонта;
- производитель, модель, теги, программа и комментарий;
- предварительный поиск похожих двигателей.

Категории similarity:

```text
LIKELY_SAME_MOTOR
POSSIBLE_ANALOGUE
SAME_PROGRAM_ONLY
```

### Ограничение

Текущая similarity-функция не является точным сравнением полной обмотки. Она не заменяет модель всех проводников, пазов, соединений и геометрии.

### Не реализовано полностью

- группы подтверждённых аналогов;
- неразобранные/непривязанные намотки;
- полная идентичность обмотки;
- автоматическое объединение записей запрещено.


Реализованы:

### Справочник

Созданы отдельные каркасы:

```text
/sites/reference/mobile/
/sites/reference/desktop/
```

Маршрут `/sites/reference/` выбирает соответствующую версию по сохранённой настройке браузера.

Не завершено:

- ссылки на справочник должны быть проверены и добавлены во все нужные меню основного сайта;
- содержимое справочника пока является каркасом;
- статьи, схемы, таблицы и документы ещё нужно наполнить;
- общие данные справочника следует хранить отдельно от presentation-layer mobile/desktop.

## 13. CI и тесты

Присутствуют workflows:

- Arduino UNO Build;
- ESP32 Build;
- CMP Protocol Tests.

`ESP32 Build` запускает `pio run -e esp32` для изменений прошивки ESP32.

В ходе этого аудита статус текущего head не подтверждён: GitHub connector не предоставил надёжный результат workflow run для прямого commit head. Поэтому нельзя записывать `GREEN`, пока пользователь или Actions явно не подтвердит успешные проверки.

## 16. Что не считать завершённым

- persistent `session_id` allocator;
- immutable job snapshot store;
- строгая сквозная связь задания, ремонта, двигателя, запуска и катушки;
- восстановление активного задания после перезапуска;
- безопасная обработка всех отказов UART/SD/power loss;
- полный производственный журнал программы;
- автоматизированная связь расхода со стартом/завершением;
- финальное наполнение справочника;
- точное сравнение полных обмоток;
- подтверждённые группы аналогов;
- неразобранные намотки;
- полноценный проверенный генератор Al → Cu;
- мультивалютность;
- индексация/ротация крупных NDJSON;
- OTA/backup как завершённая производственная функция;
- длительные и fault-injection испытания;
- подтверждённый GREEN текущего head.

## 17. Активная точка продолжения

Не возвращаться к созданию базовых CMP-файлов или к повторной разработке уже существующего сайта.

Следующий основной этап:

```text
Persistent session allocator
+ immutable winding job snapshot
+ job_id/session_id/run_id/repair_id linkage
```

Последовательность:

1. подтвердить CI текущего head;
2. исследовать текущий путь `HTTP → OutgoingWindingJob → queueJob()`;
3. не создавать второй независимый генератор идентификаторов;
4. создать устойчивый allocator на SD;
5. создать неизменяемый snapshot задания;
6. восстановить snapshot после перезапуска;
7. связать ACK и события запуска с snapshot;
8. добавить тесты отказа SD, потери ACK, повторов и перезапуска;
9. обновить docs и handoff.

## 18. Обязательные правила для будущего чата

- Всегда работать в `cmp-protocol-v1`, пока пользователь явно не выбрал другую ветку.
- Перед ответом о готовности проверять код, а не только `main` или старые документы.
- Не повторять реализованные склад, WEB, API и Arduino-модули.
- Не называть backlog готовой функцией.
- Не считать commit успешной сборкой.
- Не включать SSR из ESP32 или WEB.
- Не превращать UNKNOWN в CU.
- Не пересчитывать историческую стоимость по новой цене.
- Не считать принятые данные выполненной намоткой.
- После значимого изменения обновлять минимум `01_CURRENT_STATE.md`, `05_COMPLETED_WORK_LOG.md`, `06_ACTIVE_WORK_AND_NEXT_STEPS.md` и при необходимости этот аудит.
