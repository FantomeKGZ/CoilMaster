# Где остановились и что делать дальше

Последняя активная работа выполнялась в:

```text
firmware/esp32/src/CM_WindingJournal.h
firmware/esp32/src/CM_WindingJournal.cpp
```

Добавлено требование: внутри одной `session_id` новый `RUN_STARTED` должен иметь `run_id`, строго больший всех ранее сохранённых запусков этой сессии.

На момент создания этого каталога пользователь ещё не подтвердил зелёную сборку именно этих двух изменений.

## Шаг 1 — обязательная проверка

Сначала проверить workflow для текущего head ветки:

```text

CMP Protocol Tests
```

Результат записать в этот файл и в `05_COMPLETED_WORK_LOG.md`.

Если сборка не зелёная:

1. открыть failed job;
2. получить точный compile error;
3. проверить совпадение объявления и реализации `loadSessionHighestRunId()`;
4. проверить, что обе функции находятся в классе и namespace `CM`;
5. исправить минимальным коммитом;
6. повторно проверить оба workflow.

Не начинать следующий функциональный этап до зелёного состояния.

## Шаг 2 — документирование текущего изменения

После зелёной сборки создать тематический документ:

```text
docs/79_MONOTONIC_WINDING_RUN_IDS_PER_SESSION.md
```

В нём зафиксировать:

- `run_id` возрастает только внутри одной `session_id`;
- новая сессия может иметь собственную последовательность;
- нулевые значения запрещены;
- старый или повторный `run_id` отклоняется;
- это защита журнала, а не команда физического запуска.

## Шаг 3 — исправить идентичность события журнала

В текущем коде есть важный риск:

```cpp
containsRunEvent(uint32_t runId, RemoteEventType type)
```

Проверка дубликата не включает `session_id`.

Также `loadRunStartSession(runId, ...)` ищет запуск только по `run_id`.

Если Arduino создаст новую сессию и снова начнёт нумерацию запусков с 1, старый запуск другой сессии может быть ошибочно принят за дубликат или за старт текущего запуска.

Следующее рекомендуемое изменение:

```cpp
containsRunEvent(uint32_t sessionId,
                 uint32_t runId,
                 RemoteEventType type)
```

И заменить поиск старта на проверку составного ключа:

```text
(session_id, run_id, event)
```

Требования к изменению:

- не ломать дедупликацию повторной отправки одного события;
- разрешить одинаковый `run_id` в разных сессиях, если такая семантика подтверждена;
- проверять точную пару session/run при завершении;
- добавить тесты межсессионного совпадения `run_id`;
- обновить документацию.

## Шаг 4 — определить устойчивую семантику session_id

До расширения производственного журнала нужно зафиксировать:

- кто генерирует `session_id`;
- когда она меняется;
- должна ли она возрастать после перезапуска Arduino;
- где хранится последнее значение;
- что происходит при потере EEPROM/настроек;
- допускается ли повтор старой session_id после полного сброса.

Без этого нельзя гарантировать глобальную уникальность составного идентификатора запуска.

Рекомендуемый идентификатор события:

```text
session_id + run_id + event_type
```

## Шаг 5 — связать доставленное задание и фактический запуск

Сейчас `JobDeliveryEvent` содержит `jobId`, а `RemoteWindingEvent` не содержит `jobId`.

Из-за этого ESP32 пока не может строго доказать, что `RUN_STARTED` относится к конкретному принятому заданию.

После фиксации семантики идентификаторов нужно спроектировать обновление протокола, которое свяжет:

- `job_id`;
- `session_id`;
- `run_id`;
- индекс катушки;
- число катушек программы;
- целевые витки.

Это изменение выполнять только одновременно для Arduino, ESP32, тестов и документации протокола.

## Шаг 6 — создать снимок задания на ESP32

Перед отправкой задания нужно сохранять серверный снимок, содержащий минимум:

- `job_id`;
- `repair_id`;
- `motor_id`;
- тип программы;
- список катушек и витков;
- выбранный материал;
- диаметр провода;
- timestamp создания;
- статус доставки;
- статус выполнения.

Событие `RUN_COMPLETED` должно обновлять этот снимок, а не создавать несвязанную производственную запись.

До появления такой связи нельзя автоматически считать ремонт полностью намотанным только по `completed_runs`.

## Шаг 7 — расширить производственный журнал

После устойчивой связи job/run добавить:

- фактический номер катушки;
- целевые витки;
- фактические витки;
- причину завершения или остановки;
- физическое подтверждение START;
- ссылку на ремонт;
- ссылку на выбранную катушку склада;
- снимок программы.

## Шаг 8 — отказоустойчивость

После завершения модели состояния проверить сценарии:

1. ESP32 перезапустилась до `JOB_ACK`.
2. Arduino приняла задание, но ACK потерян.
3. ESP32 перезапустилась после `RUN_STARTED`.
4. Arduino перезапустилась во время намотки.
5. SD недоступна при событии.
6. SD заполнилась.
7. повторно пришёл `RUN_COMPLETED`.
8. пришёл старый ACK от предыдущего задания.
9. связь восстановилась после таймаута.

Во всех случаях SSR должен оставаться под контролем Arduino и переходить в безопасное состояние.
