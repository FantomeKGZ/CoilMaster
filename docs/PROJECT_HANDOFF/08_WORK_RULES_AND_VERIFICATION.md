# Правила разработки и проверки

## Основной процесс

Для каждого изменения использовать цикл:

```text
1. Проверить актуальную ветку и head.
2. Прочитать текущий код и связанные документы.
3. Сформулировать одно небольшое инженерное изменение.
4. Обновить спецификацию или документ, если меняется контракт.
5. Изменить код.
6. Проверить объявления, реализации и места вызова.
7. Запустить сборку и тесты.
8. Исправить ошибки до зелёного состояния.
9. Обновить документацию.
10. Обновить handoff-каталог.
```

## Работа с GitHub

Активная ветка:

```text
cmp-protocol-v1
```

Перед обновлением существующего файла обязательно:

1. заново получить файл из GitHub;
2. использовать его текущий blob SHA;
3. не применять старый SHA из предыдущего шага;
4. при `409` повторно получить файл и аккуратно объединить изменения;
5. не затирать изменения, появившиеся параллельно.

Не считать успешный commit доказательством компиляции.

## Статусы проверки

Использовать только явные статусы:

### `NOT VERIFIED`

Код записан, но сборка и тесты ещё не подтверждены.

### `FAILED`

Есть красный workflow или пользователь сообщил об ошибке.

### `GREEN`

Конкретный workflow завершился успешно.

### `USER CONFIRMED`

Пользователь явно сообщил, что всё зелёное или устройство работает.

### `APPROVED`

Архитектурное решение принято и должно соблюдаться.

## Что проверять после C++-изменения

Минимум:

- совпадают ли сигнатуры `.h` и `.cpp`;
- добавлен ли новый `.cpp` в сборку автоматически;
- корректен ли namespace;
- доступны ли используемые типы;
- нет ли неоднозначного перегруженного метода;
- не используется ли неподдерживаемая функция Arduino/ESP32 SDK;
- не превышены ли буферы;
- не появились ли неинициализированные поля;
- корректны ли преобразования `uint16_t`, `uint32_t`, `uint64_t`;
- нет ли переполнения до приведения типа;
- закрываются ли файлы SD на всех путях;
- не изменяется ли состояние до завершения валидации.

## Workflow

Для изменений протокола и ESP32 проверять:

```text
ESP32 Build
CMP Protocol Tests
```

Если один workflow зелёный, а другой красный, этап не завершён.

Красные промежуточные коммиты могут оставаться в истории. Важно состояние последнего commit, а не отсутствие красных записей в общей ленте Actions.

## Правила изменения протокола

Любое изменение кадра UART требует одновременно:

- обновить ESP32;
- обновить Arduino;
- обновить тесты;
- обновить документацию;
- определить совместимость со старой версией;
- проверить поведение при неизвестном кадре;
- проверить CRC и длину;
- проверить таймауты и повторы.

Нельзя менять только одну сторону и считать протокол завершённым.

## Правила безопасности

Изменение не принимается, если оно может:

- включить SSR без физического подтверждения;
- оставить SSR включённым после ошибки;
- трактовать потерю связи как разрешение;
- автоматически продолжить намотку после перезапуска;
- запустить вторую программу параллельно;
- обойти локальную кнопку START;
- превратить кнопку `B` в удалённую аварийную перезагрузку без отдельного решения.

## Правила данных и склада

Перед записью:

- проверить ссылку на ремонт;
- проверить существование складской записи;
- проверить материал;
- проверить валюту;
- проверить остаток;
- сохранить снимок цены;
- использовать pending/recovery там, где операция состоит из нескольких шагов.

После записи:

- вернуть авторитетные итоговые значения;
- проверить контрольные суммы;
- не заставлять браузер повторно рассчитывать историческую стоимость;
- не пересчитывать старую операцию после изменения цены.

## Правила UI

Любое существенное изменение интерфейса выполнять для обеих версий:

```text
firmware/esp32/web/mobile/
firmware/esp32/web/desktop/
```

Исключение допускается только если документировано, почему функция предназначена для одной версии.

UI должен:

- показывать ошибки сервера, а не скрывать их;
- блокировать невозможную операцию;
- не подменять серверную истину локальным расчётом;
- показывать UNKNOWN как отдельное состояние;
- отображать контрольные признаки и предупреждения;
- не обещать оператору, что физическая операция выполнена, пока нет подтверждённого события.

## Правила документации

После этапа:

- создать или обновить тематический документ в `docs/`;
- записать точные имена полей API;
- указать формулу и округление;
- указать обратную совместимость;
- указать ограничения;
- указать коммиты;
- указать статус сборки.

## Definition of Done

Этап завершён только когда:

- код находится в активной ветке;
- контракт понятен;
- сборка зелёная;
- тесты зелёные;
- пользовательская проверка выполнена, если нужна;
- документация обновлена;
- handoff обновлён;
- следующий шаг явно записан.

## Формат записи новой сессии

В конец `05_COMPLETED_WORK_LOG.md` добавлять:

```text
## YYYY-MM-DD — Название этапа

Цель:

Изменено:

Файлы:

Коммиты:

Проверка:

Ограничения:

Следующий шаг:
```
