## 1. Цель нового блока

Сделать единый понятный рабочий поток учёта материалов конкретного ремонта: оператор видит материалы ремонта, выбирает реальные складские позиции, вводит фактически использованное количество, видит цену/остаток, а система создаёт прослеживаемое ручное списание и обновляет себестоимость ремонта.

## 2. Карточка «Материалы ремонта»

В карточке открытого ремонта добавить единый раздел для материалов:

- обмоточный провод: медь/алюминий, точная катушка `spool_id`, диаметр, остаток, цена;
- подшипники: тип/номер, количество, складской остаток и цена;
- расходные материалы: лак, изоляция, клинья, стеклолента/бандаж и другие позиции каталога;
- количество/масса/длина фактически использованного материала;
- стоимость строки и общий итог материалов ремонта;
- состояние строки: запланировано / подтверждено списание / корректировка.

Раздел должен одинаково работать на desktop и mobile.

## 3. Выбор материала со склада

Сделать выбор без ручного ввода складских идентификаторов:

- поиск по названию, типу, диаметру/номеру и другим релевантным полям;
- отображение доступного остатка и текущей цены прямо в результате выбора;
- быстрый список часто используемых/подходящих позиций;
- для обмоточного провода использовать только точный реальный `spool_id`;
- не позволять подтверждать расход больше доступного остатка без явного корректного складского сценария.

Не создавать скрытого автоматического выбора катушки.

## 4. Списание

Списание остаётся **явным действием оператора**.

Для RUN_WIRE сохранить существующий safety-контракт:

- `RUN_COMPLETED` — только evidence;
- никакого автоматического списания после `RUN_COMPLETED`;
- обязательны точные `spool_id`, `source_session_id`, `source_run_id`;
- повторная отправка/refresh не должна создавать двойное списание;
- при изменившемся остатке между preview и confirm выполнить authoritative reread и fail-closed validation.

Для остальных материалов обеспечить эквивалентную прослеживаемость: repair id, material/spool id, quantity, price snapshot, timestamp/operation id и корректировка отдельной операцией вместо уничтожения истории.

## 5. Цена и себестоимость

При подтверждённом списании:

- сохранять snapshot цены, использованной для конкретной операции;
- не пересчитывать старое списание задним числом после изменения текущей цены склада;
- немедленно отражать строку в material cost ремонта;
- общий costing ремонта должен однозначно объясняться суммой сохранённых операций;
- корректировка должна быть отдельной аудируемой записью.

## 6. UX и ошибки

Вместо общих ошибок показывать оператору конкретную причину и следующий шаг, например:

- «Катушка не выбрана» -> действие «Выбрать катушку»;
- «Остатка недостаточно» -> показать доступный остаток и возврат к выбору;
- «Этот запуск уже списан» -> показать существующую операцию;
- «Данные запуска изменились/не найдены» -> запретить списание и предложить обновить карточку;
- «Материал отсутствует на складе» -> перейти к складу/созданию позиции, если это разрешено текущим workflow.

Не скрывать integrity/fail-closed ошибки за автоматическим исправлением.

## 7. История и исправления

Карточка ремонта должна показывать историю материальных операций:

- исходное списание;
- кто/когда (если текущая модель пользователя это хранит);
- источник RUN_WIRE для провода;
- корректирующие операции;
- итоговое фактическое количество и стоимость.

Никакого удаления подтверждённой истории ради «редактирования» прошлой операции.

## 8. Проверки и invariants

Обязательно сохранить:

- no automatic physical START;
- no auto-resume after reboot;
- Arduino — единственный владелец SSR;
- ESP32/Web не управляет SSR напрямую;
- `RUN_COMPLETED` не списывает провод;
- exact spool/session/run provenance;
- restore/operator recovery остаётся fail-closed;
- append-only/integrity ledgers не заменять опасными tail-only shortcut;
- не вводить unbounded whole-file buffering растущих NDJSON;
- не делать автоматическую truncation/rotation production data;
- не начинать преждевременную миграцию в БД/индекс без отдельного решения.

## 9. Порядок реализации

3. Реализовать read-only список/preview материалов ремонта и складской selector.
4. Подключить подтверждаемое списание обычных материалов с idempotency/integrity guards.
5. Интегрировать существующий exact RUN_WIRE flow в тот же UI, не ослабляя его контракт.
6. Добавить price snapshot + costing aggregation.
7. Добавить историю и корректировки append-only способом.
8. Довести desktop/mobile parity.
9. Добавить host/web tests: duplicate submit, insufficient stock, stale preview/TOCTOU, missing exact spool/run provenance, correction history, costing consistency, reload/recovery.

Составить точную карту текущего data flow и определить минимальные точки расширения. Не писать новый параллельный ledger и не менять safety invariants до завершения этого аудита.
