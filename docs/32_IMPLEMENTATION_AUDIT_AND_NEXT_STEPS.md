# CoilMaster — аудит реализации и следующие шаги

Дата проверки: 2026-08-05
Ветка: `cmp-protocol-v1`

## 1. Что уже реализовано

### Arduino Uno

- модульная прошивка Arduino Uno;
- конечный автомат намотки;
- ввод программы катушек с клавиатуры 4×4;
- кнопки A/B/C/D, `*`, `#` и внешняя кнопка START;
- управление SSR с безопасным состоянием LOW при запуске;
- подсчёт витков по SS49E;
- пауза и продолжение;
- ручной режим без подсчёта;
- один сигнал после катушки и три сигнала после всей программы;
- сохранение незавершённого состояния и идентификаторов в EEPROM;
- очередь событий Arduino → ESP32 с ACK/NACK и повторными попытками;
- приём удалённой программы от ESP32 без автоматического включения SSR.

### CMP и UART

- формат пакетов CMP v1;
- CRC;
- парсер и диспетчер;
- подтверждения и отрицательные подтверждения;
- повторная передача;
- события начала и завершения прохода;
- передача удалённой программы намотки;
- тесты протокола на ПК;
- автоматические сборки Arduino и ESP32 в GitHub Actions.

### ESP32

- Wi-Fi точка доступа;
- локальный HTTP-сервер;
- UART2 для связи с Arduino;
- приём и подтверждение событий Arduino;
- журнал намоток на microSD;
- отправка программ на Arduino с ожиданием `JOB_ACK`;
- API состояния и отправки задания;
- сервер статических файлов с microSD;
- мобильная и ПК-версия CoilMaster;
- мобильная и ПК-версия справочного сайта;
- автоматическое открытие соответствующей версии справочника;
- резервная встроенная страница, если каталог `/web` отсутствует.

### Склад — первая рабочая версия

- хранение бухт в `/data/warehouse/spools.ndjson`;
- хранение движений в `/data/warehouse/movements.ndjson`;
- группировка остатка по диаметрам;
- подсчёт активных бухт;
- расход за выбранный месяц;
- расход за всё время;
- API `GET /api/warehouse/summary?month=YYYY-MM`;
- мобильная страница `/mobile/warehouse.html`;
- ПК-страница `/desktop/warehouse.html`;
- вывод общего остатка, числа бухт и расхода.

### Документация

Зафиксированы архитектура системы, оборудование, протокол, база данных, рабочий процесс, склад, две версии интерфейса и сайты с microSD.

## 2. Найденные незавершённые места

### Критически важные

1. Нет телеметрии текущей катушки и текущего количества витков в реальном времени.
2. События завершения пока не содержат полного снимка программы и типа обмотки для надёжного восстановления истории.
3. Нет полноценного подтверждения оператором: `повторить программу` или `завершить сессию`.
4. Нет создания и редактирования клиентов, двигателей и ремонтов через WEB.
5. Нет привязки отдельных записей намотки к ремонту и карточке двигателя.
6. Склад пока только читается: нет API добавления бухты, прихода, взвешивания после ремонта и подтверждённого списания.
7. Нет реального модуля резервного копирования на FTP/сетевой сервер.
8. Нет FTP-доступа к microSD.

### Требующие упорядочивания

- `CM_WarehouseWeb` создан как отдельный модуль, но текущий маршрут склада пока зарегистрирован непосредственно в `main.cpp`. На следующем этапе необходимо оставить одну реализацию и убрать дублирование.
- Временная логика прогресса в WEB использует условные проценты. После телеметрии она должна рассчитываться по фактическим виткам.
- Месяц для склада сейчас передаёт браузер. После подключения DS3231 ESP32 должна уметь определять текущий месяц самостоятельно.
- На microSD нужно копировать каталог `firmware/esp32/web` как `/web`; автоматическая загрузка WEB-файлов при прошивке пока не реализована.

## 3. Принятые ограничения безопасности

- WEB не включает SSR напрямую.
- Получение программы от ESP32 не запускает двигатель.
- Запуск производится клавишей `A` или внешней кнопкой START.
- Между катушками требуется отдельное подтверждение START.
- Arduino остаётся самостоятельным контроллером безопасности при отсутствии ESP32.

## 4. Ближайший порядок реализации

### Этап A — завершить складскую сводку

1. Вынести маршрут `/api/warehouse/summary` из `main.cpp` в `CM_WarehouseWeb`.
2. Добавить API списка конкретных бухт выбранного диаметра.
3. Добавить форму новой бухты с обязательными полями:
   - диаметр;
   - текущий вес.
4. Дополнительные поля оставить необязательными:
   - марка;
   - производитель;
   - поставщик;
   - партия;
   - цена;
   - комментарий.
5. Добавить операцию повторного взвешивания:
   - вес до;
   - вес после;
   - вычисленный фактический расход;
   - подтверждение списания.

### Этап B — телеметрия намотки

Добавить события:

- `RUN_STATE`;
- `COIL_PROGRESS`;
- `COIL_COMPLETED`;
- `PROGRAM_COMPLETED`;
- `PROGRAM_REPEAT_REQUESTED`;
- `PROGRAM_FINISHED`.

Минимальные поля прогресса:

- `job_id`;
- `session_id`;
- `run_id`;
- номер текущей катушки;
- всего катушек;
- текущие витки;
- целевые витки;
- состояние: ожидание, намотка, пауза, готово.

### Этап C — база мастерской

После стабилизации телеметрии и склада:

1. клиенты с обязательным телефоном;
2. поиск по нормализованному номеру;
3. технологические карточки двигателей;
4. ремонты как связь клиента и двигателя;
5. привязка завершённых намоток к ремонту;
6. рабочая и пусковая обмотки;
7. вес одной обмотки × количество;
8. фактический расход бухт.

### Этап D — резервное копирование

- три последние локальные копии на microSD;
- внешняя копия на FTP или сервер в локальной сети;
- проверка целостности перед удалением старой локальной копии;
- FTP-доступ к microSD с режимом только чтения по умолчанию.

## 5. Текущая контрольная точка

Проект уже имеет стабильную аппаратную и коммуникационную основу. Следующая практическая задача — не начинать новые большие разделы, а довести склад до полного цикла:

`добавление бухты → вес до → вес после → фактическое списание → статистика`.
