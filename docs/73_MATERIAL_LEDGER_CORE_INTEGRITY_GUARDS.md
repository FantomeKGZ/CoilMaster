# Защита целостности внутри MaterialLedger

Проверки ссылки на ремонт и валюты дополнительного материала теперь выполняются не только в HTTP-обработчике, но и внутри `MaterialLedger::confirmUsage()`.

## Проверка ремонта

Перед созданием номера операции и до изменения складского остатка выполняется:

```cpp
repairExists(usage.repairId)
```

Если ремонт отсутствует в `/data/workshop/repairs.ndjson`, метод возвращает `false`.

При этом:

- `usage_id` не резервируется для записи;
- pending-транзакция не создаётся;
- остаток материала не меняется;
- строка расхода не добавляется в журнал.

## Проверка валюты

После чтения активного материала и до расчёта стоимости проверяется:

```cpp
currency == "KGS"
```

Материал с устаревшей или неподдерживаемой валютой не может быть списан даже при прямом вызове `MaterialLedger::confirmUsage()` в обход веб-API.

## Зачем нужна двойная проверка

HTTP-обработчик возвращает оператору подробные ошибки `repair_not_found`, `material_not_found` и `unsupported_material_currency`.

Проверка внутри `MaterialLedger` является последней линией защиты для будущих внутренних вызывающих модулей. Она не позволяет сохранить некорректную операцию, если новый код забудет выполнить предварительную проверку на уровне интерфейса.
