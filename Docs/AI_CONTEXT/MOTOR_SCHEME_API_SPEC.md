# Motor Scheme Binding REST API Specification

Status: `PROPOSED`

Priority: `P1`

Date: 2026-08-07

## 1. Purpose

Define a small, safe REST contract for reading, creating, changing and removing the `winding_reference` stored in a CoilMaster motor record.

This API stores references only. It does not transfer or duplicate handbook HTML/images and must never control winding hardware.

Related document: `Docs/AI_CONTEXT/MOTOR_SCHEME_BINDING_SPEC.md`.

## 2. Data ownership

- ESP32 Motor Database owns the motor record and its selected binding.
- Handbook scheme catalog owns `CM-SCH-*`, `CM-CON-*`, images, metadata and all available connection options.
- The motor record stores only the selected identifiers plus small audit metadata.

## 3. Stored object

Recommended persisted object:

```json
{
  "winding_reference": {
    "version": 1,
    "scheme_id": "CM-SCH-XXXXXXXXXXXX",
    "connection_id": "CM-CON-XXXXXXXXXXXX",
    "catalog_version": 3,
    "bound_at": "2026-08-07T11:00:00Z",
    "binding_source": "user",
    "verification": "confirmed"
  }
}
```

`connection_id` is optional. A motor can be bound to a winding-layout scheme without selecting a concrete connection option.

## 4. Preferred dedicated endpoints

Use dedicated binding endpoints instead of forcing the web UI to replace the complete motor object for a small scheme change.

```text
GET    /api/motors/{motor_id}/winding-reference
PUT    /api/motors/{motor_id}/winding-reference
DELETE /api/motors/{motor_id}/winding-reference
```

The ordinary motor endpoints may still include `winding_reference` in the returned motor record.

## 5. Read binding

### Request

```text
GET /api/motors/MTR-000123/winding-reference
```

### Response when present

```json
{
  "ok": true,
  "motor_id": "MTR-000123",
  "revision": 17,
  "winding_reference": {
    "version": 1,
    "scheme_id": "CM-SCH-XXXXXXXXXXXX",
    "connection_id": "CM-CON-XXXXXXXXXXXX",
    "catalog_version": 3,
    "bound_at": "2026-08-07T11:00:00Z",
    "binding_source": "user",
    "verification": "confirmed"
  }
}
```

### Response when no binding exists

Return `200`, not `404`, because the motor exists and an empty binding is a normal state.

```json
{
  "ok": true,
  "motor_id": "MTR-000123",
  "revision": 17,
  "winding_reference": null
}
```

## 6. Create or replace binding

### Request

```text
PUT /api/motors/MTR-000123/winding-reference
Content-Type: application/json
```

```json
{
  "expected_revision": 17,
  "winding_reference": {
    "version": 1,
    "scheme_id": "CM-SCH-XXXXXXXXXXXX",
    "connection_id": "CM-CON-XXXXXXXXXXXX",
    "catalog_version": 3,
    "binding_source": "user",
    "verification": "confirmed"
  }
}
```

`bound_at` should normally be generated by ESP32 when the write succeeds rather than trusted from the browser.

### Successful response

```json
{
  "ok": true,
  "motor_id": "MTR-000123",
  "revision": 18,
  "winding_reference": {
    "version": 1,
    "scheme_id": "CM-SCH-XXXXXXXXXXXX",
    "connection_id": "CM-CON-XXXXXXXXXXXX",
    "catalog_version": 3,
    "bound_at": "2026-08-07T11:05:12Z",
    "binding_source": "user",
    "verification": "confirmed"
  }
}
```

## 7. Remove binding

### Request

```text
DELETE /api/motors/MTR-000123/winding-reference
Content-Type: application/json
```

Optional body:

```json
{
  "expected_revision": 18
}
```

### Response

```json
{
  "ok": true,
  "motor_id": "MTR-000123",
  "revision": 19,
  "winding_reference": null
}
```

Deleting the binding must never delete a handbook scheme, image, catalog entry or connection option.

## 8. Optimistic concurrency

Motor cards can be open in two browser tabs or edited by two devices. A small revision number prevents one browser from silently overwriting a newer edit.

Rules:

- every successful motor mutation increments `revision`;
- client sends `expected_revision` when known;
- if stored revision differs, return HTTP `409 Conflict`;
- response includes current revision so UI can refresh and ask the user what to do.

Example:

```json
{
  "ok": false,
  "error": "revision_conflict",
  "expected_revision": 17,
  "current_revision": 18
}
```

The UI must not silently retry a conflicting write.

## 9. Validation levels

Validation must be explicit about what ESP32 can prove.

### Level A — structural validation, always available

ESP32 validates:

- `scheme_id` matches approved `CM-SCH-*` format;
- `connection_id`, when present, matches approved `CM-CON-*` format;
- supported binding `version`;
- supported `binding_source` and `verification` values;
- request size limits.

### Level B — catalog validation, when compact catalog/index is locally available

ESP32 may additionally verify:

- `scheme_id` exists;
- `connection_id` belongs to that `scheme_id`;
- catalog version compatibility.

If the local catalog is unavailable, lack of Level B validation must not make the Motor Database unusable. Store the structurally valid reference with an appropriate verification state instead of pretending it was catalog-verified.

## 10. Parameter consistency

The selected scheme may conflict with motor parameters such as slots, rpm, poles, q, pitch or branches.

Recommended policy:

- browser/handbook performs rich comparison and warns before save;
- ESP32 does not recompute winding theory;
- if a locally cached catalog provides enough metadata, ESP32 may reject an impossible ownership relation (`connection_id` not under selected `scheme_id`), but should not independently choose a different scheme.

The user remains responsible for confirming the technical selection.

## 11. Error responses

Recommended HTTP status codes:

- `200` — successful read/delete or empty normal state;
- `400` — malformed JSON/request;
- `404` — motor record does not exist;
- `409` — revision conflict;
- `413` — request exceeds configured size;
- `422` — structurally valid JSON but invalid binding values or proven catalog ownership mismatch;
- `500` — storage/internal error.

Example validation error:

```json
{
  "ok": false,
  "error": "connection_not_owned_by_scheme",
  "scheme_id": "CM-SCH-...",
  "connection_id": "CM-CON-..."
}
```

## 12. Atomic storage requirement

A binding write must be atomic from the Motor Database point of view.

Required behaviour:

1. load the motor record;
2. validate revision and payload;
3. update only `winding_reference`;
4. persist through the approved storage service;
5. increment revision only after successful persistence;
6. return the stored object.

Do not write directly to SD files from the HTTP route handler if the project has a Motor Database/storage service abstraction.

## 13. Existing motor compatibility

Old records without `winding_reference` remain valid.

Reading them returns `winding_reference: null`.

No bulk migration is required merely to introduce this feature.

## 14. Browser integration

The intended UI flow is:

```text
Motor editor
   -> Scheme Picker
   -> returns scheme_id + optional connection_id
   -> PUT /api/motors/{id}/winding-reference
   -> Motor Scheme Widget refreshes from saved record + handbook catalog
```

The Scheme Picker must not persist data by itself.

The compact Motor Scheme Widget must remain read-only except for explicit edit/remove actions that open the normal editor/picker flow.

## 15. Security and hardware isolation

These endpoints mutate database metadata only.

They must not:

- start/stop winding;
- operate relay/SSR/buzzer;
- send direct hardware commands;
- bypass application services or CMP;
- expose arbitrary filesystem paths.

## 16. Acceptance criteria

- existing motors without a binding continue to load;
- binding can be read, created/replaced and removed;
- one motor stores one `scheme_id` and zero or one selected `connection_id`;
- multiple available connection options remain owned by the catalog, not copied into the motor record;
- stale edits produce `409` rather than silently overwriting data;
- binding writes are atomic;
- removing a binding does not affect handbook files;
- no hardware-control path is introduced;
- offline/unavailable handbook does not prevent normal motor-record access.
